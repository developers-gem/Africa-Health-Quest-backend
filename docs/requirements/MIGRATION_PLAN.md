# Migration Plan — Lovable prototype → Africa Health Quest platform

**Target stack:** React + Vite + TypeScript + Tailwind + shadcn/ui (web) · Node.js + Express + TypeScript (API) ·
MongoDB + Mongoose · Flutter + Dart (Riverpod, Dio, GoRouter, SQLite) · Anthropic Claude API (server-side).

**Approved decisions that shape this plan** (`docs/decisions.md`): D1 new repository · D2 start fresh (no user/progress/review
data migration; **content is migrated verbatim**) · D3 server-side guest accounts upgraded in place · D4 missions hidden until
clinician-approved · D5 only admins edit content.

**Already built ahead of this audit** (commit `bbb130c`, 50 passing tests): monorepo, shared contracts + OpenAPI, Express API
core, authentication (email + verification, Google ID token, guest + upgrade, rotating refresh tokens, password reset),
RBAC (`player` / `reviewer` / `admin`), audited role administration. These rows are marked ✅ below.

## Guiding principles

1. **Preserve every existing feature and all content text.** Behaviour changes are limited to the defect fixes listed in
   `TECHNICAL_RISKS.md`, each of which needs product-owner sign-off (see §4).
2. **Server-authoritative:** the API is the only place that knows answer keys, computes scores, rolls random events,
   grants rewards and unlocks content. Clients render and submit choices.
3. **One contract:** every endpoint is defined once in `packages/api-contracts` (zod → OpenAPI). React uses the TS types;
   Flutter generates Dart models from `docs/api/openapi.json`.
4. **No big-bang cut-over:** the Lovable prototype stays live until the new web app reaches feature parity and passes
   acceptance (§5).

## 2. Data migration

| Data                                                         | Action                                                                            |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Users, sessions, progress, reviews in Supabase               | **Not migrated** (D2). Announce the reset to existing testers.                    |
| Missions, countries, tiers, Commander events, debrief levels | Migrated verbatim by seed script; legacy copy kept in `legacy/lovable-prototype/` |
| Hero image                                                   | Migrated and optimised                                                            |
| Review history                                               | Not migrated (no approvals exist — every mission shows "Awaiting review" in S02)  |

Because of D4, **no mission will be visible to players until a clinician approves it in the new system.** Launch therefore
depends on reviewer availability (risk R-20).

## 3. Cut-over sequence

1. API content + gameplay endpoints reach parity (Phases 3–6).
2. Web app reaches screen parity; side-by-side visual comparison with `audit-evidence`.
3. Clinician(s) approve the 10 missions in the new review workspace.
4. Soft launch web on a staging domain; product owner acceptance (§5).
5. Production launch; prototype URL redirected or retired.
6. Flutter beta (internal testing tracks), then store release.

## 4. Behaviour changes requiring product-owner approval

Listed with recommended defaults in `TECHNICAL_RISKS.md §Product decisions needed` (Q1–Q8). Until approved, the
migrated engine reproduces the prototype rules exactly, except where a rule is a security defect (client-side scoring,
answer exposure), which is non-negotiable under the project instructions.

## 5. Parity acceptance checklist

- [ ] All 12 features in EXISTING_FEATURE_INVENTORY reachable on web and mobile.
- [ ] 10 missions / 17 steps / 38 choices / 5 countries / 4 tiers / 4 Commander events present, text identical (automated).
- [ ] Scoring golden tests pass for every mission (all-correct, all-wrong, mixed, replay).
- [ ] No API response to a player contains `correct` or `feedback` for an unanswered step (automated contract test).
- [ ] Debrief produces the four sections for each of the 6 levels; errors map to friendly messages.
- [ ] Reviewer can approve / request changes; editing content invalidates approval; badge reflects latest decision.
- [ ] Guest → account upgrade keeps all progress; two devices show identical progress.
- [ ] Header and all screens render without wrapping defects at 360, 390, 768 and 1280 px.
